# KICKOFF — building exp with a multi-agent session

This repository contains a complete specification and the prior art to port from. Code is not
written yet (except the hardened measurement schema in `shared/`). This file tells a fresh build
session how to proceed.

## 1. Read in this order

1. `SPEC.md` — purpose, principles, architecture, decisions (D1–D13), milestones and acceptance (§9).
2. `docs/spec/09-work-packages.md` — the parallel plan: ownership, waves, gates, review rules.
3. `docs/spec/01-contracts.md` — every interface. This is what makes parallel work safe.
4. The component spec for the work package you are on (`02`–`06`, `10`), plus `07-security.md` and `08-operations.md`.
5. `reference/README.md` — what the prior art is and which functions to port.

## 2. How to run the build

1. **WP-0 first, alone** (integrator): JSON Schemas, OpenAPI, `shared/python/exp_common`, fakes,
   fixtures (including the converted EXM outage fixture). Review and merge before anything else.
2. **Fan out WP-1 … WP-7 in parallel**: one builder and one reviewer per WP, each confined to its
   owned paths, each building against the contracts and fakes, M1/M2 scope first.
3. **WP-8 (integrator)** builds the container harness and runs the milestone gates M1 → M2 → M3 → M4,
   then **WP-9** and the M5 scope across WPs, then the M5 gate; then **WP-10/11** (speedtest
   analytics, `docs/spec/12-speedtest-analytics.md`) and the M6 gate.
4. Contract changes only through change requests (`09-work-packages.md` §5).
5. A milestone is done only when its acceptance suite (`SPEC.md` §9) passes in CI.

## 3. Environment needed

- Ubuntu 22.04/24.04 build host (VM is fine) with Docker able to run `--privileged --cgroupns=host`
  containers (harness, systemd package tests), Python 3.10+, Node 20+, `wrangler`.
- Local manager development and tests use `wrangler dev` / `@cloudflare/vitest-pool-workers` with
  local D1/R2 — **no Cloudflare account is needed until the A2.1 deploy test.**
- No lab hardware, EdgeConnect, or Mist access is needed: the harness simulates the event LAN, and a
  documentation-built fake Orchestrator covers drills in CI.

## 4. Things the build session must not do without the owner

- Deploy to a real Cloudflare account, create real Access applications, or push to a remote.
- Run drills against real appliances or networks.
- Commit any secret, token, or private key (the release signing key is generated by the owner
  outside the repo; use a throwaway key for tests, stored outside the repo).
- Import from `reference/` or copy its configuration files.

## 5. Paste-ready kickoff prompt

> You are building **exp** from the specification in this repository. Read `KICKOFF.md`, then
> `SPEC.md`, `docs/spec/09-work-packages.md`, and `docs/spec/01-contracts.md`. Act as the
> integrator. Execute WP-0 first and get it reviewed. Then run WP-1 through WP-7 in parallel, one
> builder and one reviewer per work package, each restricted to its owned paths and building
> against the frozen contracts and fakes, M1/M2 scope first. Then build the harness and run the
> milestone gates (WP-8) in order M1 → M2 → M3 → M4, then WP-9 and the M5 gate, then WP-10/11 and the M6 gate. Port logic from
> `reference/` where the component specs say so, citing sources, never importing it. Every
> enforcement control needs a test that attempts the forbidden action. Do not deploy to Cloudflare,
> push to remotes, or touch real networks. Report progress per milestone with the acceptance results.
